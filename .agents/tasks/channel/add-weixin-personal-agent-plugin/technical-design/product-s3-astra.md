**Keep installation and wiring separate. Give the Dispatcher a terminal-free way to change its own channel.** A valid Dispatcher already has at least one channel, onboarding defaults to Feishu, and the requirement excludes Feishu and Weixin together. Appending Weixin to the usual installation would leave the operator in an unsupported configuration. I recommend allowing an explicitly named channel to be replaced. The ruling to add to an existing Dispatcher does not authorize replacing its route. (`config/config.ts`, `readDispatcherChannels`, `onboard/wizard.ts`, requirement, “Non-goals”.)

**1. Who runs what.** The syntax needs a ruling. I use `PKG` below for `@excitedjs/weixin-channel`.

- The Dispatcher or a person runs `dreamux plugin add PKG`, without a terminal, while Dreamux runs. This installs and registers the package for the next daemon start. Apply the adjudicated plugin-directory-only lookup. (`plugin/manage.ts`, `resolve.ts`, adjudication L1–L6.)
- Either runs `dreamux channel add PKG --dispatcher ID` to append, or supplies `--replace CHANNEL_ID` to switch that binding in place. Weixin needs no provider settings under the design, so either path can run without prompts. If the package offers several channels, let the caller name the provider or reuse the existing terminal choice. A repeat must leave one binding per provider. (`config/config.ts`, final design §3.)
- The person runs `dreamux plugin run PKG login` in a terminal and scans. Dreamux already passes arguments and inherited stdio to the package. I recommend that Weixin use the sole configured Weixin binding or ask the person to choose among several. That targeting rule needs approval so the login command and the session agree on whose credential to use. (`plugin/run.ts`, requirement behaviors 2 and 11.)
- After successful login, the Dispatcher or person runs `dreamux daemon restart`, without a terminal. This activates the change for the whole daemon. The operator sends a WeChat DM and checks for a reply. Until restart the existing route is available for coordinating the handoff. (`cli/commands/daemon.ts`, final design §12, requirement criteria 2–4.)

**2. Where wiring belongs.** Dreamux owns Dispatcher channel entries. Write only the selected binding, preserving unrelated keys, values and order. Byte-for-byte whitespace preservation would add a text-editing contract beyond criterion 10. Keep the existing provider collector for channels that need settings. Today `channel add` requires a TTY and refuses existing IDs. It calls onboarding, which asks for cwd and runtime, drops unknown keys during the rewrite and runs doctor after writing. A missing login could therefore make a successful write look like failure. Moving wiring into each plugin would make every package learn Dreamux’s config schema. (`onboard/channel-add.ts`, `wizard.ts`, `run.ts`, `config/raw-file.ts`, adjudication C1–C3.)

**3. Which commands earn their place.** Keep `plugin add`, `channel add` and `plugin run`. A package can contribute runtimes or several channels, so installing it cannot identify a binding. The package owns its verbs. I recommend deferring `plugin remove` and `plugin list`, subject to a ruling on criteria 13–14. That postpones safe uninstall and per-registration diagnostics. Both can ship independently of first contact. (`plugin/loader.ts`, `manage.ts`, adjudication R1–R4.)

**4. Smallest delivery.** Ship those three commands with the installable Weixin package, its login and session, then have the operator verify a DM and reply after restart, restart again, and confirm receipt resumes without another scan or a duplicate message. Slice 1 still awaits its revised login/state design. I did not verify live delivery. If replacement is declined, settle a supported initial Dispatcher configuration before promising the fresh-install story. Defer the Feishu onboarding redesign. (Task README, requirement criteria 9–11.)

**5. What will hurt later.** A successful configuration change can disappear if `config.agents.replace` writes the daemon’s earlier snapshot before restart. The operator explicitly assigned that window to a later change. Keeping doctor separate lets the operator check readiness after login, when the result is meaningful. (`config/service.ts`, requirement behavior 13, adjudication C1–C3.)
