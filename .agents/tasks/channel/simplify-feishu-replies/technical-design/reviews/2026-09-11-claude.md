## Verdict

**Blocked on two persisted-state consequences, plus one open ownership question
that gates the largest simplification the requirement asks for.**

The presentation decision is sound and the mention simplification is the real
entropy win: three outbound mention mechanisms collapse to one, and inbound
mention identity gains a single owner. The identity-array requirement is
justified by source — I verified it independently rather than accepting it.

What is not yet sound is the stored-shape half. The plan's rule for it is one
sentence (`final.md:196-199`) and that sentence, read against the three stores it
actually touches, produces an upgrade in which **every** Team and **every** Agent
on disk becomes unreadable, silently. Two of those three stores have no reader
that is even capable of failing loud, so the plan's stated safety mechanism
("readers validate the new array shape") does not exist at those two sites and
cannot be assumed into existence. This is not a migration request — the operator
excluded migration — it is a request that the plan name which values are rejected
and what the operator must do about it.

Separately, against the operator's emphasis (「重点关注代码复杂度，尽可能把能删的机制
都删干净」), the plan's net effect on the transport package is **+1 rendering
pipeline, not -1**: the entire card pipeline is retained and a native-post
pipeline is added beside it. That may be the right call, but it rests on one fact
the plan asserts and does not establish.

## Findings

### F1 — Every persisted record carries an explicit `null`, which the plan's rule rejects, and the Team reader cannot fail loud (blocker, confirmed at source)

**Scenario.** An operator upgrades. Their dispatcher holds Team `alpha`, created
before the upgrade with no identity prompt at all. Its `record.json` contains
`"leader_identity_prompt": null`. A Feishu group is bound to `alpha`. The
operator sends one message to that group.

**Source.**

- `packages/dreamux/src/service/team-service/index.ts:238` writes
  `leader_identity_prompt: identityPrompt` unconditionally, and
  `packages/dreamux/src/service/agent-entity/identity-store.ts:179` writes
  `identity_prompt: input.identityPrompt ?? null` unconditionally. **An explicit
  `null` is present in every record and every `identity.json` a released build
  ever wrote** — this is not limited to Teams that have an identity prompt.
- `final.md:196-199`: "No guidance is represented by `[]` in stored records.
  Readers validate the new array shape instead of silently discarding it,
  converting old scalar records, or retaining nullable/scalar alternatives."
  Under that rule, `null` is not the new shape and is not a retained alternative.
- `packages/dreamux/src/service/team-collection/store.ts:84-98` — `TeamStore.get`
  wraps `readTeam` in `try { … } catch { return null }`. Its own comment states
  the intent: "Missing, malformed, and unreadable are the same answer on purpose".
  There is no `LegacyStateError` chokepoint anywhere in `team-collection` (grepped).
- `packages/dreamux/src/service/agent-entity/identity-store.ts:144-158` — the
  identity reader rethrows **only** `LegacyStateError`; any other throw is logged
  at `warn` and becomes `null`. A plain `Error` from a new array check is
  swallowed exactly as the Team reader swallows it.

**Consequence (traced end to end, every gate).**

`TeamStore.get` → `null` → `TeamCollection.mustTeam`
(`team-collection/index.ts:331-338`) throws `TeamNotFoundError` — I read that gate
rather than relying on the comment at `errors.ts:5-9` that describes it ("missing,
malformed, and unreadable all arrive here. The name is free again."). Then:

1. `FeishuChannel.submit` (`feishu-channel.ts:364-369`) catches `TEAM_NOT_FOUND`
   and returns `{ status: 'rejected' }`.
2. `FeishuChannel.deliver` (`feishu-channel.ts:422-444`) calls
   `routeReconciliation.forgetTeamRoutes(plan.teamName, …)` — the **durable
   binding rows are removed from the routing document**.
3. `rejectedDeliveryNotice` (`feishu-route-reconciliation.ts:28-30`) returns
   `'silent'` for every code except `TEAM_CLOSED`. **The group is told nothing.**
4. The message is re-submitted with `null` and answered by the Dispatcher Agent.
5. `TeamStore.create` overwrites anything that is not a valid record, so the name
   `alpha` is now free and a new Team can be created over the old directory.

The same upgrade hits the Agent identity store in parallel, with three different
outcomes by role — worth separating, because only one of them is loud:

- **TeamLeader (loud, traced).** An identity that reads back `null` makes
  `leaderForOpenTeam` (`team-service/leader-agent.ts:266-271`) throw "has no
  aligned TeamLeader identity".
- **Dispatcher Agent (silent overwrite, traced).** `ensureDispatcherIdentity`
  (`dispatcher-service/identity.ts:62-88`) treats `existing === null` as "no
  identity yet", constructs a fresh record with `session_id: null`,
  `skill_sources: []`, `intent: null`, `status: 'stopped'`, and calls
  `identities.upsert(...)` — **overwriting the file on disk**. The dispatcher's
  persisted provider session id is lost, so the Agent restarts with no
  conversation continuity, and its persisted admin-supplied skill sources are
  dropped. Nothing throws and nothing is announced. This is the most damaging leg
  and the plan names this exact field in its owner table (`final.md:184`: "the
  Dispatcher's empty-list initialization").
- **Dispatcher-scoped TeamMates (inferred, not traced).** I did not read this path
  end to end. From the store's documented name-occupancy invariant, the expected
  outcome is that the entity stops resolving while its directory name stays
  reserved; treat that as an inference, not a confirmed trace.

Net: after upgrading, **every** Feishu-bound Team stops answering and its bindings
vanish without a message to the group; the Dispatcher Agent answers instead and
silently loses its own session continuity. The Teams do disappear from
`team.list`, so the state is observable — but no error is raised on the Team or
Dispatcher legs, and the operator's only diagnostic is a swallowed `warn` line.
The affected population is exactly this feature's target population.

**The plan is also ambiguous about which values it rejects**, and the two readings
differ by two orders of magnitude in blast radius:

- Strict reading (`null` rejected because nullable alternatives are not retained):
  every Team and every Agent, as above.
- Lenient reading (`?? []` at the reader, only a stored *string* rejected): only
  Teams/Agents that actually carry an identity prompt.

The plan must state which. I am not guessing on the operator's behalf.

**Smallest correction (two options; I recommend (a)).**

(a) Accept a stored scalar as a one-element list at the two readers —
`readLeaderCreationInputs` (`team-collection/store.ts:370-387`) and
`readIdentity` (`identity-store.ts:463-465`) — one ternary each. This loses no
fact, mirrors exactly what the plan already does at the MCP boundary
(`final.md:177-178`: "Keep string schemas and parsing; wrap before calling the
existing internal creation method"), and is not migration machinery: nothing is
rewritten on disk and no second shape survives past the reader.

(b) If the operator wants strict rejection, then the plan must additionally give
`TeamStore` the fail-loud path it does not have (a `LegacyStateError` that
`get`/`list` rethrow, matching `service/legacy-state.ts`), and must state the
`BREAKING:` + `Rebuild:` change note — see F3.

Either way the plan's one sentence at `final.md:196-199` is not sufficient: it
asserts a reader behavior that two of the three affected stores do not have.

### F2 — The Feishu routing document has no per-row reader at all, so `spaces[].identity` is validated nowhere (blocker, confirmed at source)

**Scenario.** A Collaboration Space `space-demo` was bound before the upgrade with
`identity: "Answer in Chinese."`. After the upgrade, a new chat under that space
triggers automatic provisioning.

**Source.** `packages/channel/feishu-channel/src/routing/store.ts:145-180`
`validated()` checks exactly four things — object-ness, `version`, `channel_id`,
and that `bindings`/`spaces` are arrays — and then returns
`spaces: document.spaces` **cast through unchecked**. There is no per-row
validation of any `FeishuSpaceRecord` field, today or in the plan.
`routing/document.ts:70` types the field `identity: string | null`.

**Consequence.** The string `"Answer in Chinese."` arrives inside a record whose
declared type is now `string[] | null`. `feishu-provisioning.ts:199-255` passes it
into `team.create`. Whichever way the implementer writes the channel-side append
the requirement asks for (「channel 层可以自己 append 一条」), the outcome is bad
and type-checking cannot catch it: a spread produces a per-character fragment list
(`['A','n','s','w',…]`, each character becoming its own `<system-reminder>` block
at the provider), and a strict array check at the Core command boundary produces a
provisioning failure whose message points at the command, not at the stale row.

The plan's protection — "Readers validate the new array shape" — has no reader to
attach to here. This site needs to be named explicitly, because unlike the Team
and Agent stores it does not even have a validation function to amend.

**Smallest correction — and this is the same breaking-vs-not choice as F1, so
decide both together.** Two options exist here as well:

(a) *Non-breaking, matching F1(a).* Wrap at the one site that reads
`space.identity` into provisioning (`feishu-provisioning.ts:199-255`), accepting a
stored scalar as a one-element list. No version bump, no operator action.

(b) *Breaking, recommended.* Bump `FEISHU_ROUTING_DOCUMENT_VERSION` from `1` to `2`
(`routing/document.ts:24`). This is the mechanism the document header already
designates for exactly this situation: "There is no migration path. A document
from an incompatible version fails loud and the operator recreates the bindings
through the Channel's own MCP tools."

I recommend (b) here even though I recommend (a) for F1, and the asymmetry is
deliberate: the Team and Agent stores *have* validating readers whose type checks
are the natural home for a wrap, whereas this store has no per-row reader at all.
Putting a field-specific ternary inside a provisioning call site — in a store that
otherwise trusts every row it loads — is a special case in the layer that does not
own the fact. The routing document already owns a version for precisely this, and
using it costs one line. If the operator prefers a uniformly non-breaking upgrade,
(a) is available and the trade is explicit: one special case bought, one loud
failure given up.

### F3 — The version bump makes this upgrade-blocking, and the change-note bullet does not say so (medium, confirmed at source)

**Scenario.** The operator runs `dreamux serve` after upgrading, with an existing
routing document on disk.

**Source.** `routing/store.ts:95` calls `validated()`, which throws on a version
mismatch. `load()` is called from `FeishuChannel.initialize()`
(`feishu-channel.ts:208`), which is awaited inside
`input-source-lifecycle.ts:246` `initializeChannelSessions`, itself awaited inside
`doStart()` with no swallowing catch on that leg. A throw there fails dispatcher
start.

The plan's only change-note instruction is `final.md:455-457`: "Generate Rush
change notes for the changed channel/transport contracts and internal
identity-array representation. Record the new format accurately;
compatibility/migration work is excluded by the operator's explicit ruling."

**Consequence.** Under the repository's changelog rule, `BREAKING:` means exactly
"the upgraded daemon or CLI cannot start until the operator performs that
migration by hand" — which is precisely what F2's correction produces. A change
note that omits `BREAKING:` and `Rebuild:` here ships an upgrade that dies at
daemon start with no recorded recovery action. (Also note the 0.x rule: record it
as type `minor` with the `BREAKING:` note leading, never type `major`.)

**This finding is conditional on F2 taking option (b).** If F2 takes (a) and F1
takes (a), nothing here is upgrade-blocking and an ordinary change note is
correct — but the plan must then say that explicitly too, because its current
silence reads as "no breaking change" without having established it.

**Smallest correction.** Add one sentence to the delivery section: if the routing
document version bumps, that change and the identity-field shape change carry
`BREAKING:` + `Rebuild:` notes naming the exact operator action — delete the routing state file
and re-run `bind_channel` / `bind_space`, and rebuild affected Teams. Whether the
Team/Agent stores also need a `Rebuild:` depends on which F1 option the operator
picks: option (a) needs none, option (b) needs one.

### F4 — Retaining `render/` makes this a net +1 pipeline in the transport package, against the operator's stated emphasis, and the retention rests on one unverified fact (high; operator decision needed)

**Scenario.** The operator asked for 「尽可能把能删的机制都删干净」. The plan
(`final.md:403-412`) keeps the whole card renderer, `editText`, `applyMentions`,
and `mentionName`, and adds a native-post construction path beside them.

**Source.** `packages/channel/feishu-transport/src/render/` is 576 lines across six
files. Retained under the plan and unreachable from any reply path after it:
`FEISHU_CARD_ELEMENT_HARD_CAP` (200) and `CARD_ELEMENT_SAFE_CAP` (180),
`TABLE_COLUMN_HARD_CAP` (50) with its column-halving, `CELL_MAX_BYTES` (4 KB) with
`validateCellSizes`, `TABLE_DEFAULT_PAGE_SIZE`, `splitTableByRows`' header repeat,
the `# h1` → card-header promotion, `replaceAtMentions`' `<@ou_…>` shorthand
(`render/render.ts:33-52`), and `packIntoCards`. The plan then adds a post packer,
a table-header prefix, and a trial-serialization loop for the 28 KB budget. A
maintainer of this package after the change must hold **both** pipelines and know
which of the two size regimes applies to which send verb.

**The retention rests on one fact the plan asserts rather than establishes.**
`final.md:403-412` says removing the public APIs "would require a separate
operator decision about external capability loss", and `final.md:425-427` says
`FeishuTransport.send` "is a public in-process API also used by an external proxy
consumer, as documented by the package README". That is a README claim about a
sibling repository. **Whether that consumer actually imports
`renderMarkdownToCards`, `editText`, `applyMentions`, or `mentionName` is not
verifiable from this worktree**, and I did not verify it. It is checkable in about
one minute by someone with the sibling checkout, and it is worth checking, because
it is the difference between deleting 576 lines plus four public symbols and
keeping them forever.

Two secondary points the plan should settle regardless of the answer:

- **Severability.** The new post splitter wants exactly the behavior
  `splitMarkdownByBytes` already has (fence repetition across a split, `Intl.Segmenter`
  grapheme boundaries) — that is genuinely necessary local logic and must not be
  rewritten. But it currently lives at `render/split.ts`. If the post path imports
  it from there, `render/` becomes non-severable and can never be deleted cleanly
  later. The plan should say that the byte splitter moves out of `render/` to a
  neutral module, leaving `render/` as a pure card concern that a future operator
  ruling can delete in one commit.
- **Scope text provenance.** `final.md`'s scope sentences ("does not authorize
  removing the package's public behavior") are leader-authored inferences, not
  operator quotes. The operator's recorded words on this axis are 「把整体逻辑简化
  一下，现在太复杂了」 and 「尽可能把能删的机制都删干净」. Per the repository's
  "operator rulings are quoted, never stretched" rule, the plan should label the
  retention as its own judgment awaiting a ruling, not as an existing boundary.

**Smallest correction.** Replace the assertion with a question the operator can
answer: state the concrete retention cost (the mechanism list above), state that
the sibling-repo import check is the deciding fact and who can run it, and move
`splitMarkdownByBytes` out of `render/` so the deletion stays available either way.

### F5 — Deleting `promoteMarkdownCode` changes behavior on paths the plan does not name (medium, confirmed at source)

**Scenario.** A peer bot sends a legacy rich post (no `content_v2`) containing a
fenced code block. Today the receiving model sees a `code` part.

**Source.** `feishu-channel/src/feishu-message-render.ts` —
`contentPartsForEvent` returns `textPartsWithMentions(raw, event.mentions)` early
for `text` messages and runs `.flatMap(promoteMarkdownCode)` on **every other**
path: post, card, and fallback. `promoteMarkdownCode` (`:235-272`) is the channel's
own fence scanner. In transport, `parse/post.ts` `renderTextNode` re-fences nodes
carrying `style:['code']`, so legacy-post code reaches the channel as fenced
*text*, and it is the channel scanner that currently promotes it.

`final.md:344-348` deletes the scanner and states "Transport owns these code
boundaries and emits code parts", but the surrounding paragraph describes the new
detection in terms of native Markdown and card markdown. It does not say that
transport's new code detection also covers legacy `content` post text nodes and
the fallback path.

**Consequence.** If the implementer reads that paragraph as scoped to `md` nodes
and card fields, a peer bot's legacy post silently loses its `code` part — a
representation regression on exactly the peer-bot interop the operator asked to
preserve. It is an ambiguity, not a stated error, but it is the kind that a green
test suite will not catch because the deleted scanner's tests go with it.

**Smallest correction.** One sentence naming the three source kinds transport's
code detection must cover after the deletion (native `md`, legacy `content` text
nodes, card markdown fields), and one validation bullet asserting a legacy post
with a fenced block still yields a `code` part.

### F6 — `sendInteractiveCard`'s four branches collapse to two (simplification, confirmed at source)

**Scenario.** Not a defect; a deletion this task is positioned to take and does not.

**Source.** `packages/channel/feishu-transport/src/transport/outbound-card.ts:14-56`
has four branches over two independent booleans — signal present × reply/create —
including a cast to a `MessageApiWithReply` shim to reach the reply endpoint
through the SDK. Meanwhile `transport/cot.ts:149`, `:195`, and `:213` already use
the generic `client.request<…>` form for this package's other endpoints, and
`feishu-session-ops.ts:185-213` confirms the signal is genuinely optional at the
only caller.

**Consequence of not doing it.** The task rewrites the send path anyway; leaving
the four-branch shape means a maintainer still holds an SDK-vs-`client.request`
split and a cast that exists only to reach one endpoint.

**Smallest correction.** Add one bullet: the outbound send path uses
`client.request` uniformly and passes `signal` only when defined, collapsing four
branches to two (reply vs create) and deleting the `MessageApiWithReply` cast.

## Mechanism ledger

Enumerated by name, as the operator's emphasis requires.

**Genuinely removed (confirmed at source, all reachable today):**
`mention_user_ids` in the reply tool schema and its parse
(`tools/messaging-tools.ts`), `optionalStringArray` (its sole caller),
`mentionUserIds` on `OutboundTarget` (`contract/outbound.ts`), `mentionUsers` on
`ChannelOutboundTarget` and its mapping in `channelOutboundToFeishuTarget`
(`bot.ts:200-208, 346-362`), `textWithLeadingMentions`
(`transport/feishu.ts:652-656`), the `mention_count` log field
(`feishu-session-ops.ts:177`), the channel's `textPartsWithMentions` +
`extractRawText` raw-body reparsing, and `promoteMarkdownCode`
(`feishu-message-render.ts:235-272`). **Inbound mention identity goes from three
owners (text reparse in the channel, post parser, card parser) to one owner in
transport** — that is the single largest real entropy reduction in this plan and it
should be stated as such.

**Replaced by a native Feishu mechanism:** leading-mention prepending →
inline `<at user_id="ou_xxxxxxxx">Name</at>` in the post body; card element
packing → one `md` node per row; card content sizing → the post's own 30 KB
document limit (held at the existing 28 KB budget per the operator's 「那就先保持
28kb 吧。」); `renderMarkdownToCards`' Markdown interpretation → Feishu's own `md`
node rendering; the `<@ou_…>` shorthand → native XML written directly by the model.

**Remaining necessary local mechanisms (each has a named failure scenario):**
the 28 KB serialized-content budget with trial serialization (the platform rejects
oversize sends), `splitMarkdownByBytes`' fence repetition and grapheme boundaries
(a naive byte split produces an unterminated fence and a broken grapheme), table
header repetition across a split (a continuation page with no header is
unreadable), and inline/fenced code detection before mention or image promotion (a
code example containing `<at …>` must stay literal).

**Net complexity for `@excitedjs/feishu-transport` as the plan stands: +1
pipeline.** Card rendering, card packing, and every card cap listed in F4 are all
retained, and a post pipeline is added beside them. The channel package is a clear
net reduction; the transport package is not, and the plan should say so plainly
rather than leave it to be discovered.

## R1 — F1: the inaccurate `null` assertion, and the actual missing contract

### What was wrong

F1 states "**An explicit `null` is present in every record and every
`identity.json` a released build ever wrote**". That is wrong. The writers
(`team-service/index.ts:238`, `identity-store.ts:179`) always store the *field*,
but its *value* is `input.identityPrompt ?? null` — `null` only when no identity
prompt was configured, and the configured string when one was.

The conclusion does not need the false claim. **Both** stored forms — `null` and a
configured string — are scalars, and neither is the proposed array. So the
incompatible population is still every Team record and every `identity.json`; the
accurate reason is "the field is always present and always scalar", not "the field
is always `null`". The blast-radius reading in F1 stands; its supporting sentence
does not, and the two sub-readings I listed collapse: under the plan's rule as
written there is no lenient reading that spares untouched Teams, because `null`
is as much a scalar as a string is.

### Plan promise vs. today's implementation

These must not be conflated, and F1 partly did:

- **Today**, neither reader validates an array shape, because the field is not an
  array yet. `readTeam` (`team-collection/store.ts:283-297`) and
  `readLeaderCreationInputs` (`:370-387`) both throw a **plain `Error`**;
  `readIdentity` coerces a non-string `identity_prompt` to `null`
  (`identity-store.ts:463-465`).
- **The plan promises** (`final.md:196-199`) that readers will validate the new
  shape. I do not dispute that the implementer would write that validation.

So the gap is not missing validation. **The gap is the error-propagation
contract**: the plan never says what *type* the new validation throws, and at both
Team-side chokepoints a plain `Error` is invisible.

- `TeamStore.get` (`store.ts:93-97`) catches everything and returns `null`. There
  is no `LegacyStateError` rethrow anywhere in `team-collection`.
- `AgentIdentityFile.read` (`identity-store.ts:144-158`) rethrows **only**
  `LegacyStateError`; every other throw is logged at `warn` and becomes `null`.

**The exact missing contract, stated precisely:** new-shape validation must throw
`LegacyStateError`, and `TeamStore.get`/`list` must gain the rethrow that
`identity-store.ts:149` already has. Without both halves, validation that is
written correctly still produces the silent outcomes traced in F1.

### Withdrawing the scalar-acceptance recommendation

F1 recommended option (a): accept a stored scalar as a one-element list at the two
readers, arguing it "mirrors exactly what the plan already does at the MCP
boundary". **That analogy is wrong and I withdraw the recommendation.** The
string-valued MCP boundary is a *designed forward contract* — the operator ruled
「但是 mcp 这里保留字符串啊」 and it stays a string permanently, for reasons of tool
ergonomics. Reader-side scalar acceptance is something else entirely: accepting a
*historical* on-disk form so an old file keeps working. That is compatibility
behavior whether or not anything is rewritten to disk, and the requirement
excludes it (「不需要考虑 breaking change」). I should not have proposed it.

### Smallest coherent failure boundary using existing mechanisms

No new migration, ledger, or normalization layer is needed, because both stores
already have the two mechanisms this requires:

1. **A record version that both readers already gate on.** `TeamRecord.version`
   (`team-collection/types.ts:92`) is checked at `store.ts:285`;
   `AgentEntityIdentity.version` is checked at `identity-store.ts:432`. Bumping
   both to `2` makes every pre-upgrade record fail at the version check — one
   comparison, already written, no per-field scalar detection anywhere.
2. **An existing fail-loud error type with rebuild guidance.**
   `service/legacy-state.ts` already owns `LegacyStateError` and the rebuild
   message shape, and `identity-store.ts:412` already throws it for a prior
   format change (`provider_ref`). Throwing it on version mismatch reuses that
   path verbatim.

The only genuinely new line is the one-line `LegacyStateError` rethrow that
`TeamStore.get`/`list` lack. That is closing a hole in an existing contract, not
adding a mechanism: it makes `TeamStore` behave the way `AgentIdentityFile`
already does.

This is also strictly simpler than what the plan currently implies. Version-gating
means no reader ever has to recognize, describe, or branch on the old scalar form
at all — the field-level array check becomes an ordinary current-shape check with
no history in it.

### The product-policy choice, labelled as such

The consequence of the above is that **on upgrade, every existing Team and every
existing Agent identity fails to load and must be recreated by hand.** That is
user-visible capability loss on upgrade. Under this repository's rules it is a
requirement decision for the operator, not an engineering call, and I am not
inferring authorization for it. I am stating only that *if* the no-compatibility
requirement is applied literally to these fields, this is the cheapest coherent
way to make the failure loud; whether that cost is acceptable — and whether these
two fields are even worth a full rebuild versus being left scalar and the array
carried only in memory — is the operator's to rule on. Note the third option the
plan has not considered: nothing forces the *persisted* shape to change at all.
The operator's requirement 「给他整条链路改成数组」 concerns the prompt-assembly
chain; keeping `identity_prompt` scalar on disk and building the array at the
assembly seam would make R1, R2, and F3 disappear entirely. I raise it as an
option for the operator, not as a recommendation that overrides a stated
requirement.

## R2 — F2: `validated()` exists; what it lacks is per-row checks

### The narrower fact

F2 says the routing document has "no per-row reader at all" and, in one place,
"no validation function to amend". That understates what is there.
`routing/store.ts:145-180` `validated()` **does** exist and is the document's
reader. It checks the envelope: object-ness, `version` against
`FEISHU_ROUTING_DOCUMENT_VERSION`, `channel_id` against the configured channel,
and that `bindings` and `spaces` are arrays. What it lacks — and this is the whole
of the finding — is **per-row field validation**: it returns
`spaces: document.spaces` cast through, so no `FeishuSpaceRecord` field is ever
checked. The consequence in F2 is unchanged; only the characterization was loose.

### Why the check belongs at `validated()`, not at provisioning

F2 offered an option (a): wrap the stale scalar at
`feishu-provisioning.ts:199-255`. **I withdraw that option.** Two reasons, both
from the source:

1. `validated()` is the store's existing single chokepoint for what counts as a
   valid document, and `document.ts:1-20` states that ownership explicitly: "the
   filename, the schema, and what counts as a valid document are this Channel's to
   decide". A field check there is the owner enforcing its own schema.
   Provisioning is a *consumer* of `space.identity`; a check there is a special
   case in a layer that does not own the fact, and it protects only that one call
   site while every other reader of `spaces[]` stays unguarded.
2. The version check is **already inside `validated()`** (`store.ts:156-158`). So
   raising `FEISHU_ROUTING_DOCUMENT_VERSION` adds no mechanism whatsoever — it
   changes one integer in the place that already reads it. That is why this, and
   not a consumer-side wrap, is the minimal change.

### Not inferring authorization for the rebuild

F2 and F3 presented the version bump as recommended and treated the
`document.ts:18-20` header ("the operator recreates the bindings through the
Channel's own MCP tools") as settling what happens next. **It does not.** That
header records the intent of a previous decision; it is design evidence, not an
operator ruling authorizing a destructive rebuild in *this* change. Bumping the
version means every operator loses their existing routing document and must
re-run `bind_channel` / `bind_space` for every bound conversation before their
Feishu channel works again — a manual, destructive, user-visible action.

So the corrected shape of this finding is: the defect is that `spaces[]` rows are
unvalidated while the plan changes a field inside them; the owner of any fix is
`validated()`; and **whether the fix is a version bump (loud, costs every operator
a manual rebuild) or a per-row field check that rejects only malformed rows is a
product-policy decision the operator must make.** I name the mechanism and the
owner; I do not authorize the rebuild. This is the same decision as R1's, and the
two should be ruled on together so the upgrade has one posture.

## R4 — F5: the corrected legacy-post code scenario

### What was wrong

F5 claimed a peer bot's legacy post with a fenced code block loses its `code`
part, via `renderTextNode` re-fencing. Reading both functions in full, that
mechanism is wrong on both ends:

- **Native code nodes are already handled in transport and never depended on the
  channel scanner.** `parse/post.ts:80-90` handles `tag: 'code'` and
  `tag: 'code_block'` and pushes a structured `{ kind: 'code', code, language }`
  part directly. Deleting `promoteMarkdownCode` cannot affect them.
- **`renderTextNode` produces an inline code span, not a fence.**
  `parse/post.ts:155-176` sizes a backtick run to one longer than the longest run
  inside the text (minimum one backtick) and pads it — an inline span. Meanwhile
  `promoteMarkdownCode`'s opener is
  `/(^|\n)( {0,3})(`{3,}|~{3,})([^\r\n]*)\r?\n/` — it requires **three or more**
  markers followed by a newline. The channel scanner therefore never promotes
  `renderTextNode`'s output, and no `style: ['code']` node loses anything.

### The actual input path that regresses

The scanner's only real input is **fenced markdown sitting inside the text of a
part that transport emitted as `text`**. Concretely, after the plan's own
`content_v2` selection lands, this is the path:

A peer Dreamux bot replies with a native post. Its `content_v2` row is
`{"tag":"md","text":"Here:\n```ts\nconst x = 1\n```"}`. `parse/post.ts:74-79`
(the `md` branch) appends that string verbatim as a **text** part — it does no
Markdown interpretation at all. Today `contentPartsForEvent`
(`feishu-message-render.ts:121-124`) runs `.flatMap(promoteMarkdownCode)` over it,
the scanner finds the fence, and the receiving model sees
`<code language="ts"><![CDATA[const x = 1]]></code>`. Delete the scanner and, unless
transport emits a `code` part for that fence itself, the model sees the raw fence
as ordinary text.

The same applies to two other text-producing sources: a multi-row legacy post
whose plain `text` rows spell out a fence (rows are joined with `\n` at
`post.ts:32` and merged by `appendTextPart`, so a fence spanning three rows
becomes one text part containing a fence), and card `markdown`/`lark_md` fields,
which `parse/card.ts:150-155` collapses into text parts.

The sharpest scenario is the first, because **this task creates it**: the reply
format Dreamux is switching to is precisely `md` nodes carrying raw Markdown, so
bot-to-bot code exchange runs through this path on every reply.

### Why the plan does not already cover this

`final.md:395-401` requires transport to "interpret inline and fenced code
boundaries before promoting a tag or image reference; code examples remain code."
That is a *suppression* rule — do not turn `<at …>` inside a fence into a mention.
It is a different job from **emitting** a `code` part. An implementer can satisfy
that sentence completely and still emit the fence as text.

### Smallest correction, within the owner the plan already chose

One clause in the same paragraph: transport's `md`-node handling emits a `code`
part for each fenced block it finds in the node text, converging on the same
`{ kind: 'code', code, language }` shape the `code`/`code_block` tag branch
already produces at `post.ts:80-90` — so the code-part contract has one producer
shape, not two. Nothing moves out of transport and no new entity appears. Plus one
validation bullet: an `md` node whose text contains a fenced block still yields a
`code` part with its language preserved.

- The **release note is still right** and should stay: `send` is a published API

- The **premise is not established** and should be narrowed. The plan should not
  assert that an external consumer calls `FeishuTransport.send`; the demonstrated
  external dependency is on the *renderer* helpers, and the one consumer that has
  been examined implements its own transport. Per the repository's rule that a
  design record's claims are evidence-backed, the smallest correction is to
  replace the asserted caller with what is actually known: the package is
  published, `send`'s contract changes, and the confirmed external coupling is to
  `renderMarkdownToCards` / `cardToContent` / `mentionName`.

This matters beyond wording. The `send` sentence is currently doing load-bearing
work in the plan's scope argument, and it is the weaker half of that argument. The
renderer retention survives on its own evidence; the `send` claim should not be
left propping it up on evidence that does not exist.
