## Verdict

**Sound, no blocking correctness defect found.** The reply-path plan is a genuine
entropy reduction: it deletes the mention-plumbing chain and the reply-path card
rendering, and replaces both with native Feishu `post + md` the platform already
renders. The inbound corrections and the identity-array change are correctly
scoped to the operator's explicit mandates and their owners are identified at the

(one medium-high, on changelog documentation of a persisted-state break; one

## Findings

### F1 (medium-high) — The identity representation change breaks three persisted files, and the plan documents the code waiver but not the changelog consequence

**Scenario.** A daemon running a released Dreamux has on disk `identity.json`
(`identity_prompt`, `agent-entity/types.ts:85` is `string | null`), `record.json`
(`leader_identity_prompt`, `team-collection/types.ts:113`), and a space binding
document (`identity`, `routing/document.ts:70`), all scalar-or-null. After this
change all three become `string[]`, and the plan says readers must "validate the
new array shape instead of … converting old scalar records, or retaining
nullable/scalar alternatives." On the next start, `readIdentity`
(`agent-entity/identity-store.ts:463-466`) — or its new array validator — rejects
the old scalar/null value, so the entity reads as "no identity" and the existing
Team/Agent cannot be restored.

**Consequence.** This is a persisted-state upgrade blocker: the operator cannot
upgrade and keep existing Teams without a manual rebuild. The plan is silent on it.
The operator's ruling "不需要考虑 breaking change" (requirement.md) waives
*compatibility/migration code* — it does not state whether it also waives the
standing changelog rule (root `CLAUDE.md` "Changelog Responsibility": an
incompatible persisted-state shape "leads with `BREAKING:` and includes `Rebuild:`
with the exact manual action"). The plan's delivery section says only "compatibility
/migration work is excluded by the operator's explicit ruling," which covers code
and leaves the documentation obligation unaddressed.

**Smallest correction.** In `final.md`'s "Validation and delivery", add one sentence
that either (a) commits the identity.json / record.json / space-document shape
change to a `BREAKING:` + `Rebuild:` change note with the exact manual action, or
(b) records the operator's verbatim waiver as also covering changelog documentation.
This is a one-line decision, not a design change, and should be adjudicated before
development authorization.

### F2 (medium) — `sendIntroduceAck` is the last in-process production caller of the card renderer, and the renderer-ownership accounting omits it

**Scenario.** `h.bot.send` (the text→card path) has exactly two callers today:
`sendReply` (`feishu-session-ops.ts:149`) and `sendIntroduceAck`
(`feishu-session-ops.ts:645`). After the reply path moves to native post, the only
in-process production caller of `transport.send` → `renderMarkdownToCards` is the
introduce ack — a plain-text, mention-free string (`introduceAckText(peers)`).
`renderMarkdownToCards`/`pack.ts`/`table.ts`/`constants.ts` therefore stay
production-reachable for a single plain-text message, while the explicit card paths
(`sendCard`/`editCard`/COT) never used `renderMarkdownToCards` at all.

**Consequence.** The plan's "Public API boundary and remaining renderer" section
names `sendCard`, `editCard`, question/binding cards, and COT as remaining card
paths, but not `sendIntroduceAck`. Given the operator's stated priority ("把能删的
机制都删干净"), this is the one seam the plan leaves unexamined: the introduce ack
could equally be a native post, which would make the whole card renderer
production-dead (public `editText`/`renderMarkdownToCards` export excepted).

**Smallest correction.** Either record `sendIntroduceAck` explicitly as a
deliberately-remaining card-render caller with its reason, or list it as the
follow-up simplification (operator decision) that would retire the card renderer
from production. Not a blocker; a boundary the plan should not leave implicit.

### F3 (low) — The native-post splitter reuses card-renderer-owned `render/split.ts`; the dependency direction is unrecorded

**Scenario.** The plan reuses "the existing Markdown tokenization/splitting
primitives" (`marked.lexer` plus `splitMarkdownByBytes` in `render/split.ts`) for
the new oversized-post splitter, while also noting that splitter "alone does not
establish that serialized payload invariant." `splitMarkdownByBytes` is exported
from the card render module (`render/render.ts:29`), so the new native-post path
would import from the card renderer's split helper.

**Consequence.** A later decision to retire the card renderer (F2's follow-up)
would orphan the post splitter's byte/fence/grapheme helper. It is a mild
ownership smell, not a defect, but the plan does not state where the reused
primitives home.

**Smallest correction.** In the splitting section, name the home of the reused
primitives and state that the post splitter must depend only on the byte/fence/
grapheme helpers, never on card-specific constants (`CARD_CONTENT_SAFE_BYTES`,
element caps). One sentence of cleanup-trail.

## Confirm-at-implementation (already flagged by the solution; do not under-scope)

These are not findings against the plan — they are the plan's own known limits,
restated so the TeamLeader treats them as implementation gates rather than
incidental notes:

1. **MCP `teamCreatePayloadHash` must hash the array form.** The Team MCP delegate
   hashes `leader.identity` (`team-collection/mcp-delegate.ts:140-149`) and the
   Feishu provisioning path invokes `team.create` with `space.identity`. After the
   change both must feed the same array-form input into the hash, or replay/
   idempotency diverges. The plan flags this; it is easy to miss because the
   string-vs-array difference is invisible at the payload boundary.
2. **Card-merge mention dedup must not erase distinct identities sharing a name,
   nor intentional repeats within the primary view.** The plan names both traps;
   the `mergeInteractiveContentParts` change is the subtlest part of the inbound
   work and needs its own focused tests.
3. **Exported `InboundContentPart` union gains a `mention` variant** — external
   exhaustive consumers break; the release note must lead with it (the plan says
   so; confirm it is not buried).
4. **Unverified platform facts to close before/at implementation:** empty-name
   `<at user_id="…"></at>` client appearance (pairing reminder and peer-bot
   mention), native `content_v2` image-resource extraction (no live image probe),
   and 28 KB as an operating budget rather than a measured native-post limit.

## Mechanism accounting (the operator's stated review priority)

**Removed (net entropy reduction).** `mention_user_ids` across tool schema →
session opts → `sendReply` → `ChannelOutboundTarget` → `OutboundTarget`
(five hops, one fact); `textWithLeadingMentions` and the `mention_count` log
field; `replaceAtMentions` from the reply path; the reply path's card rendering;
the channel's `promoteMarkdownCode` scanner and `textPartsWithMentions` raw-text
reparse (the mention/code facts move to transport, where parsing belongs).

**Native Feishu replacements.** Inline XML mention → platform-rendered mention
(no local prepend/translate); `post + md` heading/table/code rendering → platform
rendering (no card-native element conversion).

**Remaining local mechanisms (necessary, and who asked for them).** The post
encoder + 28 KB splitter (Feishu's 30 KB post limit + the operator's "先保持28kb"
and "code/table boundaries"); the inbound semantic mention parser across
text/post/card/native-md (the operator's interop mandate); the identity array +
string-only MCP boundary + creation-time reply guidance (the operator's explicit
representation and reply-address requirements). The only mechanism the solution
itself invents beyond the operator's words is the table-header repetition in the
splitter — small, and directly paid for by "meaningful table boundaries."

**Resulting complexity.** Net negative on the reply path. The inbound-parser and
identity-array additions are operator-mandated scope, not solution-invented
surface. The one thing to watch is that the inbound work is presented as a unified
"ordered mention part" mechanism; that unification is defensible (text, post, and
card all share the same fact: a mention with id + name + position), but the card
merge is where the unified model costs the most and should not grow beyond the two
named merge scenarios.

## Recheck of F1, F2, F3 (follow-up, same frozen inputs)

I re-checked the three findings against `final.md` and the cited source. Two
premises were wrong; one was overstated. Corrections below; the Verdict still
stands (no blocking correctness defect), but the finding list shrinks.

### F2 — retracted; the premise is wrong

Re-reading `final.md`: "The renderer no longer participates in reply/text-send"
and "`FeishuTransport.send` … card-to-post presentation change" mean the
*shared* text-send contract flips to post, not just the reply tool. `bot.ts`
forwards both `sendReply` and `sendIntroduceAck` to the same `transport.send`
with no rendering-mode branch (`bot.ts:271-278`), and `feishu-session-ops.ts:149`
/`:645` are the only `h.bot.send` callers. So under this solution
`sendIntroduceAck` becomes a native post too — it does **not** remain a
card-render caller, and there is no surviving production `renderMarkdownToCards`
path via `send`. The only retained renderer caller is the public
`editText` → `renderSingleCard` → `renderMarkdownToCards` path the plan
explicitly preserves.

What survives of F2 is a narrow documentation request only: the plan's
"remaining renderer" section names `sendCard`/`editCard`/question/binding
cards/COT but does not name `sendIntroduceAck` as an in-process text-send caller
whose presentation also flips card→post. Since the plan already commits to a
`FeishuTransport.send` contract release note, the ask is only to name that caller
in the note. No mechanism, no boundary, no surviving path.

### F3 — retracted; only directory placement, no card dependency

Re-reading `render/split.ts`: it has no imports, no card constants, no card
types; `splitMarkdownByBytes(text, byteBudget)` receives the byte budget as a
parameter and splits by line/fence/grapheme only. It is already card-agnostic.
The new post splitter reusing it introduces no dependency on card mechanisms —
the only observation is that the helper lives under `render/`, which is a
directory name, not a coupling. The smallest change justified by the source is
none beyond the reuse the plan already states: no new helper, no indirection
layer, no relocation needed now. F3 is not a finding; at most a footnote for
whichever change later retires the card renderer.

### F1 — corrected; keep the concrete shape change, label my interpretation

Concrete and verified: `identity.json` `identity_prompt` (`agent-entity/types.ts:85`),
`record.json` `leader_identity_prompt` (`team-collection/types.ts:113`), and the
space document `identity` (`routing/document.ts:70`) all change from
scalar-or-null to `string[]`, and the new reader validates the array shape rather
than accepting the old scalar/null.

I overstated the documentation gap. The requirement already commits to release
notes ("Include their tests, release notes, and owning documentation"), and the
plan's delivery section says "Generate Rush change notes … Record the new format
accurately." The plan is not silent on documentation.

My reading that the operator's "不需要考虑 breaking change" waives only migration
*code* was my interpretation, not a settled ruling. Labeled as such, the one
genuinely open point is: should the persisted-shape change lead with
`BREAKING:`/`Rebuild:` under the standing root `CLAUDE.md` changelog rule, or be
recorded as a plain contract-change note under the operator's verbatim waiver?
That is a documentation-policy question to confirm with the operator, not a
finding against the plan. Separately, the concrete upgrade consequence of the
shape change (whether an old `identity.json` fails loud or reads as absent on the
new validator) should be confirmed at implementation, since it determines which
note form is honest.
